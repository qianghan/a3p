# P0-0 Security Audit — Supabase RLS Advisories (2026-10-16)

Branch: `cro-readiness-sprint` · Auditor: coding agent (no live credentials)

## Background

On 2026-10-06 Supabase reported CRITICAL advisories on project `agentbook-db`:
1. a public table without Row-Level Security (RLS)
2. likely-sensitive columns exposed through the API

Fix status was unknown. This audit inspects the **code** (schema, migrations,
application access paths). The live Supabase project could not be queried —
see "Owner action required" below.

## Findings

### 1. RLS is not implemented anywhere in code — CONFIRMED OPEN (code level)
- `packages/database/prisma/schema.prisma` (187 models): zero RLS directives
  (the only "rls" string matches are the substring in "urls" comments).
- `packages/database/prisma/init-schemas.sql`: no `ENABLE ROW LEVEL SECURITY`.
- All 9 migration directories: no `CREATE POLICY` / `ENABLE ROW LEVEL SECURITY`.
- `grep` for RLS/policy statements across `packages/database`, `plugins/`
  returned nothing.

### 2. Application-level tenant isolation IS consistently applied — OK
- Every backend derives `tenantId` from `(req as any).tenantId` (set by the
  Next.js proxy from the session cookie / Telegram chat mapping) and includes
  it in every query `where` clause. Spot-checked `plugins/agentbook-expense`
  (176 `tenantId` references): list, detail, split, vendor, bank-account,
  and bank-transaction endpoints all scope by `tenantId`.
- Conclusion: cross-tenant reads via the application's own API are blocked
  at the application layer, provided the proxy always sets `x-tenant-id`
  (verified pattern in `apps/web-next` proxy routes).

### 3. Supabase PostgREST Data API is not used by the app — OK (reduces exposure)
- No `@supabase/supabase-js` dependency in any `package.json`.
- No `createClient` / anon-key usage anywhere in `apps/web-next/src`.
- Backends connect via Prisma directly to Postgres (`DATABASE_URL`).
- The Oct-06 advisories therefore concern the Supabase-managed API surface
  (auto-generated PostgREST), not the application's own data path. Exposure
  requires possession of the project's anon/service key.

### 4. No keys or secrets in tracked source — OK
- `git grep` for JWT (`eyJhbGciOi`), `sb_secret_`, `SERVICE_ROLE_KEY` across
  tracked files: clean.
- `.env`, `.env.local`, `.env*.local` are gitignored (`.gitignore` lines 51–52, 101–102, 117–119).

### 5. Plaid tokens encrypted at rest — OK
- `plugins/agentbook-expense/backend/src/plaid-token-crypto.ts` (+ usage in
  `server.ts`): access tokens persisted via `encryptToken()` into
  `AbBankAccount.accessTokenEnc` (migration `add_plaid_access_token_enc`).

## Residual risk

The Supabase **Data API remains enabled by default** on the project. Any table
in an exposed schema without an RLS policy is readable via PostgREST by anyone
holding the anon key. Application-level `tenantId` filtering does NOT protect
this path. Until verified in the dashboard, the Oct-06 advisories must be
treated as potentially still open.

## Owner action required (Supabase dashboard — cannot be done from code)

1. Open Supabase Dashboard → `agentbook-db` → **Advisors → Security**: confirm
   zero critical/high findings. If the "public table without RLS" finding
   persists, either:
   - (a) enable RLS + tenant-scoped policies on every table in exposed
         schemas (note: the app uses custom cookie auth, not Supabase Auth, so
         policies must key off a session variable the backends set per
         transaction — non-trivial, do not apply blindly), or
   - (b) restrict the Data API: Database → API → disable table exposure for
         schemas the app never queries via PostgREST (the app uses none —
         Prisma only), or rotate keys and confirm the anon key is not shipped
         in any client bundle.
2. Re-run advisors after any change; keep a screenshot for the audit trail.

## Recommendation

Short term (pre-revenue): option (b) — the app does not use PostgREST, so
disabling table exposure in the Data API closes the advisor findings with
zero application risk. Long term: adopt RLS only if/when the app moves to
Supabase Auth or a session-variable tenant context.
