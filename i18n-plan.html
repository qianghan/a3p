1. Review findings

You asked me to check the design for completeness, regressions, and over-engineering. The review found five gaps and five things to cut. Three of the gaps would have shipped bugs; one would have shipped a plan whose tests didn't run at all.

Gaps found — now in the plan

GAP 1 · SEVERITY: MONEY CORRUPTION
Localizing number display without number input is a 100× money bug

14 call sites parse user-entered amounts as parseFloat(raw.replace(/,/g, '')) — strip every comma, then parse. In Canadian French, the decimal separator is a comma.

// A fr-CA user types "45,50" meaning $45.50
parseFloat("45,50".replace(/,/g, ''))  // → 4550
Math.round(4550 * 100)                 // → 455000 cents = $4,550.00

Today this is latent — no French UI exists, so nobody types French numbers. But the moment PR-3 renders 45,50 $ on screen, the app is actively teaching users to type a format it misreads by 100×, and the wrong figure is booked straight to the double-entry ledger.

Consequence for the plan: input parsing and output formatting must land in the same PR. Splitting them creates a window where the bug is live. Sites: agentbook-invoice-parser.ts:37, agentbook-estimate-parser.ts:41, agentbook-recurring-parser.ts:38, agentbook-bot-agent.ts (×5), telegram/webhook/route.ts (×2), parse-amount.ts:72, agent-corrections.ts:122, consultation-review.ts:84, agentbook-core/backend/src/server.ts:3590.

GAP 2 · SEVERITY: SILENT DATA LOSS IN OUTBOUND DOCUMENTS
Chinese text will render as blank boxes in every PDF

agentbook-invoice-pdf.ts and agentbook-tax-pdf.ts use @react-pdf/renderer with fontFamily: 'Helvetica'. Helvetica is one of the 14 standard PDF base fonts and contains no CJK glyphs. Chinese characters will drop or render as tofu boxes — in a document that goes to the user's client, not to the user.

Fix requires Font.register() with a real CJK face. Unsubsetted Noto Sans SC is ~10MB, which is too large for a serverless bundle, so this needs a subsetting step — a genuine task with a real constraint, not a one-liner. See D5.

GAP 3 · SEVERITY: THE PLAN'S OWN TESTS WOULD NOT HAVE RUN
Plugin frontend tests cannot fail CI — two independent masks

My draft put the "render every page in 3 locales, assert no raw keys leak" layer in plugins/*/frontend/src/__tests__/. That location does not gate:

  1. 3 of 6 plugins have no test script. agentbook-core, agentbook-tax, and agentbook-invoice are missing it — yet agentbook-core already has 4 test files and a vitest.config.ts sitting there unexecuted. CI runs npm test --if-present, so they are silently skipped.
  2. Even a present, failing script passes. The CI step is npm test --if-present || echo "No tests configured" — the || echo swallows a real failure into exit 0.

The in-repo comment says the mask "covers the legacy naap-fork plugin frontends (not the AgentBook launch surface)" — but the job matrix lists agentbook-billing, agentbook-career, agentbook-core, agentbook-expense, agentbook-invoice, agentbook-startup, agentbook-tax. The comment is inaccurate; the mask does cover the launch surface.

Consequence for the plan: PR-1 adds the 3 missing test scripts and un-masks the 6 AgentBook plugins. Without this, every component test in this plan is decoration.

GAP 4 · SEVERITY: WRONG COPY FROM DAY ONE
No pluralization — French would be wrong immediately

The existing t() has no plural support. "{count} expenses" cannot render 1 dépense / 3 dépenses, and French plural rules differ from English (French treats 0 as singular). Not separable from the foundation, so it goes in PR-1 via Intl.PluralRules selecting key_one/key_other. zh-CN has one form and the same mechanism covers it for free.

GAP 5 · SEVERITY: MINOR, BUT CHEAP
No lang attribute on the document root

Screen readers pick the wrong pronunciation and browsers pick the wrong CJK font fallback (Simplified vs. Traditional glyph variants differ for the same codepoint). One line in the layout, folded into PR-2.

Over-engineering cut

CUT 1
Playwright text-expansion overflow test → manual spot-check

French runs 15–20% longer than English, so layouts can truncate. But asserting "no horizontal overflow" in a headless browser is notoriously flaky and would fight the loop for no real signal. The native-speaker spot-check in D3 already looks at these screens with human eyes. Dropped.

CUT 2
Dedicated bundle-size CI job → one assertion

The point was to verify the ShellContext decision worked and catalogs didn't get inlined into all 6 UMD bundles. That's one assertion in an existing test, not a job.

CUT 3
New CI job for catalog invariants → reuse invariants

apps/web-next/src/__tests__/architecture/ already runs on any code change, un-masked, DB-free, in about a minute. It is the correct and existing home for catalog invariants. No new job.

CUT 4
Spanish and Japanese → deleted, not carried forward

The orphaned apps/web-next/src/lib/agentbook-i18n.ts has es and ja translations for 7 keys. They were never wired to anything. Carrying them into the new catalog means the key-parity invariant must permanently special-case two locales that are 7/500ths complete. Delete them; re-add a locale properly when there's demand.

CUT 5
10 test layers → 7

Cuts 1–3 and folding the API-client fetch test into PR-2's own suite bring it to 7 layers that each catch a distinct failure class. See section 5.

Verdict

Complete after adding Gaps 1–5. The four in-scope surfaces (app UI, agent chat, Telegram, email/documents) are covered, plus the two input-side surfaces the original draft missed entirely (number parsing, PDF fonts).

No regression rests on four things, not on optimism: PRs 1 and 3–7 are inert by construction; PR-3 carries byte-identical golden tests for every en-US money and date output; PRs 8–11 land dark behind a flag; and the e2e gate is a baseline superset rather than a fictional all-green.

Not over-engineered after Cuts 1–5. What remains is 12 PRs for 3 locales across 4 surfaces, of which 4 PRs are the same mechanical recipe repeated per plugin group.

2. Architecture

2.1 One package, per-request translator

Two i18n implementations exist today and neither is usable as-is:

WhatStateFate
packages/agentbook-i18n (@agentbook/i18n)Real structure — core, formatters, loader, en+fr, ~111 keys. Zero consumers. Added by c612d4f5.Becomes the single package, after the core.ts rewrite below
apps/web-next/src/lib/agentbook-i18n.tsSecond, unrelated implementation. server-only, 7 keys, 5 locales. One consumer: the rate-limit branch of the agent message route.Deleted; its 7 keys migrate into the shared catalog

The core.ts rewrite is not stylistic. Today it holds currentLocale in module scope and mutates it through setLocale(). On Fluid Compute, function instances are reused across concurrent requests — so one user calling setLocale('zh-CN') changes the language of another user's in-flight response. Replace the ambient global with a factory:

// packages/agentbook-i18n/src/core.ts
export function createTranslator(locale: string, catalog: Catalog): Translator
// returns { locale, t(key, params?) }

// setLocale() and getLocale() are DELETED, not deprecated —
// they have zero consumers today, so removal is free.

Locale binds at construction, so call sites stay terse (t('expense.saved')) while nothing is mutable across requests. formatters.ts is kept unchanged — it already takes locale as an explicit argument, so it was never part of the problem. The rewritten package must not be server-only, since the shell's client components need it too.

Catalog layout: en/, fr-CA/ (a rename of the existing fr/, which is already written in Canadian French), zh-CN/. Namespaces: the 6 that exist (common, expense, invoice, tax, proactive, calendar) plus agent for the migrated keys.

2.2 How locale reaches each surface

AbTenantConfig.locale already exists with @default("en-US"), so there is no schema migration. That is worth stating plainly: it sidesteps the known hazard where a remote Vercel build runs prisma db push --accept-data-loss and a concurrent merge from an older commit silently drops new columns.

Resolution precedence: tenant config → Accept-Language → Telegram language_code → en-US. Any unrecognised stored value falls back to en-US rather than throwing, so pre-existing rows can never break a page.

Why ShellContext rather than bundling. One catalog copy instead of six, zero per-bundle size cost, and the locale is already resolved server-side before mount so there is no flash of untranslated content. The cost is one required safety property: a CDN bundle can be newer than the shell serving it, so a plugin that finds no i18n on the context must fall back to English rather than crash. That gets its own test.

2.3 Tax and legal copy stays English

Per your decision: navigation and chrome are translated, but tax guidance, filing disclosures, and legal copy remain English with a visible "available in English only" notice. Enforced by an inverted invariant — keys matching tax.advice.*, legal.*, and filing.disclosure.* must not exist in the fr-CA or zh-CN catalogs. A future PR that helpfully "completes the translation" then fails CI, which is the point.

3. Decisions required from you

These are the only inputs the plan needs. Answer all 8 and the loop runs to completion with one deliberate stop (D1). I've marked a recommendation on each; replying "all recommended" is a valid complete answer.
D1 — MERGE AUTHORITY (the one that determines whether this is actually autonomous)
May the loop merge its own PRs after CI goes green?

This matters more than it looks: auto-deploy is ON, so merging to main deploys to production. Options:

  • (a) Loop merges PRs 1–11 unattended, then halts before PR-12 and waits for you to approve the flag flip. PRs 1–11 are either inert or flag-off, so nothing user-visible ships without your sign-off.
  • (b) Loop opens each PR and halts for you to merge. Safest, but this is no longer unattended — 12 stops.
  • (c) Full autonomy including the flag flip. No human sees a Chinese or French screen before your users do.
Recommend (a). It's genuinely unattended for all the engineering, and the single human gate sits exactly where the risk is: the moment translated copy becomes visible.
D2 — FEATURE FLAG
What is the flag key, and which flag system?

An admin flag system exists (tests/e2e/admin-feature-flags.spec.ts). The loop needs the exact key name and confirmation it should default off in all environments.

Recommend key agentbook_i18n_locales, default off, flipped on in PR-12 only.
D3 — TRANSLATION AUTHORSHIP
May the loop author the fr-CA and zh-CN strings itself?

You chose "LLM-drafted + structural tests + spot review". To be unattended, the loop must write the JSON itself. Your spot-review then happens at the D1 halt — after PRs 8–11 have merged dark, before the flag flips. That way you review the real screens, not a diff of JSON.

Recommend yes, with the review at the D1 halt on rendered screens rather than on the catalog files.
D4 — FRENCH TERMINOLOGY AUTHORITY
Which French does Canadian accounting terminology follow?

Quebec accounting French is not generic French: TPS/TVQ not TVA, facture, travailleur autonome. If the loop invents terms, the copy will read as machine-translated to exactly the users it targets.

Recommend: CRA and Revenu Québec official French as the authority for all tax and accounting nouns; the loop must use the official term or leave the key English and flag it, never invent one.
D5 — CJK FONT FOR PDFs (blocks PR-11)
How should Chinese render in outbound invoices and tax packs?
  • (a) Commit a subsetted Noto Sans SC (SIL OFL 1.1 — permissive, redistribution allowed) at roughly 1–2MB after subsetting, registered via Font.register().
  • (b) Keep all PDFs English-only in v1 and show a notice. Zero binary, zero licence question, but a zh-CN user's invoices stay English.
Recommend (a). An invoice is the artefact that reaches the user's client, so it's the worst place to stay English. OFL-1.1 explicitly permits bundling. If you'd rather not carry a binary in git at all, say so and I'll fetch-and-subset at build time instead.
D6 — DECIMAL COMMA POLICY (blocks PR-3 — this is the money one)
How should 1,500 be interpreted for a fr-CA user?

It is genuinely ambiguous: 1,500 is one thousand five hundred in en-US and one and a half in fr-CA. No parser can resolve this from the string alone, and guessing wrong is a 1000× error.

  • (a) Parse by locale, and always echo the interpreted amount back in the confirmation step — "Booking $45.50, correct?" — so an ambiguous input is caught by the user before it reaches the ledger.
  • (b) Accept both separators with heuristics (comma followed by exactly 2 digits = decimal). Fewer confirmations, but silently wrong on 1,50 meaning 1.50 vs 1,500.
Recommend (a). The confirmation already exists in the chat flow. Making the parsed amount explicit turns an invisible 100× error into a visible question, and it's the only option that's safe on genuinely ambiguous input.
D7 — NON-GOALS CONFIRMATION
Confirm these are out of scope?

Receipt/OCR and voice input language; the public marketing and landing pages; /fr/-style locale URL routes (locale comes from tenant config, so routing is untouched); and deleting the never-wired es/ja stubs (Cut 4).

Recommend confirming all four. Each is a separate piece of work with its own design questions, and none blocks the three locales you asked for.
D8 — E2E GATING BASIS
Accept baseline-superset gating instead of all-green?

The 87-spec Playwright suite does not currently pass in full. The honest gate is: record the passing set at PR-0, and require every later PR's passing set to be a superset. Demanding all-green would either block the plan on unrelated pre-existing failures or tempt the loop into deleting tests.

Recommend accepting. The loop records the baseline in step 0 and writes it into the state file, so the comparison is mechanical.

4. Autonomous execution contract

The loop is a state machine over a checked-in file. It holds no plan in context; it re-derives position from disk each iteration, so it survives restarts and context loss.

4.1 State file

docs/superpowers/plans/2026-08-17-agentbook-i18n-STATE.md — created in step 0, updated after every PR, committed with it. One row per PR:

| PR | Status                          | Attempts | PR link | Notes |
|----|---------------------------------|----------|---------|-------|
| 0  | done                            | 1        | —       | baseline: 53/95 e2e, ratchet=612 |
| 1  | done                            | 1        | #453    | |
| 2  | in_progress                     | 2        | —       | typecheck red: ShellContext generic |
| 3  | pending                         | 0        | —       | |

Statuses: pending → in_progress → done | halted.

4.2 Iteration algorithm

1. Read STATE.md.
2. If any row is `halted` → STOP. Do not attempt other PRs.
3. Pick the lowest-numbered row that is not `done`.
4. If its Attempts >= 3 → mark `halted`, write the diagnosis, STOP.
5. Execute that PR's recipe from this plan.
6. Run its Definition of Done commands, in order.
7. All exit 0 →  commit, push, open PR, merge per D1, mark `done`, continue at 1.
   Any non-zero → increment Attempts, record the failing command and its
   output verbatim in Notes, continue at 1 (which retries this same PR).
8. When all rows are `done` → STOP and report.

PRs are strictly sequential. Extraction depends on plumbing; the flag flip depends on the catalogs. The loop must never skip ahead past a non-done row, which is what rule 3 enforces.

4.3 Halt conditions — do not guess about these

  • Any D1–D8 decision is unanswered or ambiguous when first needed.
  • Definition of Done still red after 3 attempts.
  • The e2e passing set is not a superset of the recorded baseline (a real regression, distinct from a flaky spec — re-run once before concluding).
  • Any packages/database/prisma/schema.prisma change becomes necessary. This plan requires none; if one appears, an assumption was wrong.
  • A secret, credential, or environment variable is needed that isn't already present.
  • A tax, legal, or filing-disclosure string is ambiguous — leave it English and halt rather than translate regulated copy on a guess.
  • main has advanced such that a rebase conflicts non-trivially. Main moves fast here; re-verify against current main rather than forcing.
Two standing prohibitions, both from prior incidents in this repo: never push directly to main — every change goes through a PR, including one-line fixes that look inert. And never run git stash, checkout, or reset in the main checkout — other agent streams keep in-progress work there. All work stays inside this worktree.

7. Non-goals

Explicitly out of scope, pending your confirmation in D7. Each is separate work with its own design questions:

  • Input language for receipts/OCR and voice. A Chinese receipt is an input-recognition problem, unrelated to UI language.
  • Marketing and landing pages. Public SEO surface with different concerns (hreflang, per-locale routes, indexing).
  • Locale URL routes (/fr/...). Locale comes from tenant config, so routing is untouched — this keeps the change far smaller.
  • Spanish and Japanese. The 7 never-wired stubs are deleted rather than carried (Cut 4).
  • Collation. Sorting Chinese client names by pinyin needs Intl.Collator; deferred until someone asks.
